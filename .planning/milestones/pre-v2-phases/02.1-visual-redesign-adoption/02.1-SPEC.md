# Phase 02.1: Visual Redesign Adoption - Specification

**Created:** 2026-07-06
**Ambiguity score:** 0.14 (gate: <= 0.20)
**Requirements:** 6 locked

## Goal

Adopt the committed Jay-6 v3 visual redesign for the existing v1 feature set, without adding progression, sequencer, queued-toast, or new playback behavior.

## Background

Jay-6 v1 is shipped and UAT-passed: chord pads, MIDI routing, bank navigation, transpose, latch, clock mode/BPM, six playback styles, variation selection, and Rhythm Gate gate length are already implemented in `src/App.svelte`, `src/components/TopBar.svelte`, `src/components/PianoLayout.svelte`, and `src/state.svelte.ts`.

The current UI is functional but still shaped like the prototype: a wide flat TopBar with every control visible, raw numeric variation dropdowns, and a pad surface that only partially reflects the hardware-inspired direction. The sketch wrap-up has already locked the visual direction in `.planning/sketches/WRAP-UP-SUMMARY.md` and `./.codex/skills/sketch-findings-jay-6/`: dark instrument chrome, compact mono readouts, TopBar C2, lifted bevel pads, and per-style variation pickers.

This phase is the in-between visual adoption pass before milestone 2 sequencer work. It redesigns the UI for features that already exist. It does not implement the progression rail, progression authoring, sequencer, or queued variation countdown toast.

## Requirements

1. **Visual token adoption**: Existing app surfaces use the committed sketch token direction.
   - Current: `App.svelte`, `TopBar.svelte`, and `PianoLayout.svelte` use ad hoc dark grays, spacing, and typography from the prototype.
   - Target: The UI applies the sketch token system: dark instrument chrome, cream pads, compact radii, 8px-grid spacing, system UI for prose, mono readouts for numeric/symbolic instrument data, orange only for sounding pads, and steel for pending/secondary system state.
   - Acceptance: Browser screenshots at desktop, iPad, and iPhone landscape sizes visibly match the committed design direction and do not introduce a generic SaaS/control-panel palette.

2. **TopBar C2 redesign**: Existing TopBar controls move into the performance-first C2 structure.
   - Current: `TopBar.svelte` exposes output, input, channel, bank, transpose, clock, BPM, style, variation, gate, and latch as equally weighted controls in a wrapping row.
   - Target: The TopBar prioritizes performance controls and folds routing plus BPM into one status pill with a setup popover containing the existing output, input, channel, Int/Ext clock, and BPM controls. BPM remains visible and becomes read-only when clock is external.
   - Acceptance: Browser smoke verifies every pre-existing TopBar capability is still reachable and functional: output, input, channel, clock source, BPM, bank, transpose, style, variation, gate when Rhythm Gate is active, and latch.

3. **Pad surface redesign**: The existing twelve pads adopt the lifted J-6 hardware treatment.
   - Current: `PianoLayout.svelte` renders the correct 5-black/7-white layout with basic flat pad styling and orange held state.
   - Target: The pad layout remains the separate J-6 hardware rows with a clean gap, lifted bevel styling, legible chord labels, and orange fill/glow reserved for physically held or latched sounding pads.
   - Acceptance: Browser smoke verifies pointer and keyboard pad presses still light the matching pad, release/latched behavior still clears or sustains highlight correctly, and no non-sounding pad uses the active orange treatment.

4. **Per-style variation pickers**: The existing variation selection becomes style-specific without changing playback semantics.
   - Current: `TopBar.svelte` shows one raw numeric variation dropdown for all non-Hold styles.
   - Target: Hold shows no variation picker; Arp styles expose a composed picker for direction, octave range, and feel with the V-number as a derived readout; Beat exposes a note-value x straight/triplet grid; Rhythm Gate exposes 4x3 pattern tiles. Each visible option maps exactly to the existing 1..12 variation index for the active style.
   - Acceptance: Browser smoke verifies selecting variation `1`, `6`, `7`, and `12` equivalents for Arp, Beat, Rhythm Gate 4, and Rhythm Gate 5 updates `ui.variation` through the existing state path and preserves the current engine behavior.

5. **Responsive redesign coverage**: The redesigned UI remains usable across the agreed device classes.
   - Current: The app has iPad scroll/selection fixes, but the prototype TopBar and pad layout can still become cramped as controls wrap.
   - Target: Desktop, iPad-sized, and iPhone-landscape layouts keep controls reachable, avoid incoherent overlap, preserve pad playability, and retain the short-viewport scroll escape where needed.
   - Acceptance: Screenshot or Playwright/browser checks pass at desktop, iPad, and iPhone landscape viewports with no clipped controls, unreadable primary labels, or inaccessible pad rows.

6. **Existing behavior preservation**: The redesign does not change the v1 instrument contract.
   - Current: App behavior flows through `state.svelte.ts`, `App.svelte`, `EngineHost`, `tickSource`, and `midi.ts`; tests cover pure data/math while UI/MIDI behavior is browser-smoked.
   - Target: The redesign may refactor UI components and styling, but it preserves existing state semantics and does not alter MIDI timing, engine lifecycle, chord data, bank data, keyboard shortcuts, or transport behavior.
   - Acceptance: `just ci` passes, and browser smoke confirms pad press/release, latch, bank navigation, transpose, style/variation changes, gate, clock source selection, BPM editing, and MIDI routing controls still operate.

## Boundaries

**In scope:**

- Adopt visual tokens from the sketch findings for the existing app shell, TopBar, pads, variation controls, and footer/shortcut affordance if retained.
- Rework `TopBar.svelte` into the C2 performance-first structure with setup popover for existing routing/tempo controls.
- Rework `PianoLayout.svelte` styling into lifted hardware rows while preserving the existing pad mapping and press/release contract.
- Replace the raw numeric variation dropdown with per-style controls that map to the existing variation indices.
- Preserve existing gate control for Rhythm Gate styles.
- Verify desktop, iPad, and iPhone landscape layouts in browser.

**Out of scope:**

- Progression rail display - it does not exist in the current app and would be a new feature.
- Progression authoring/data mechanism - future milestone/backlog item, not a redesign of existing UI.
- Sequencer UI or behavior - milestone 2 work.
- Bottom-center queued/countdown toast - the current app has no queued variation state or countdown feedback, so this would be new behavior.
- Hardware OP-1 UAT - unnecessary for a UI redesign when existing MIDI behavior is preserved and browser smoke covers the controls.
- New playback styles, chord banks, persistence, presets, velocity, multi-channel routing, or Web Audio scheduler work - unchanged project out-of-scope items.

## Constraints

- Use the existing stack: Svelte 5 runes, Vite 6, TypeScript strict, scoped component CSS, and Vitest.
- Do not add a component library for this phase; the sketch direction is custom instrument UI and the existing project has no UI library.
- Keep the existing Web MIDI locality constraints and browser targets: Chrome/Edge desktop and iPad via Web MIDI Browser.
- Do not edit `src/banks.data.json`; chord data is unrelated to this phase.
- Preserve existing state and engine contracts unless a UI-only adapter is needed to map per-style controls back to `ui.variation`.
- Verification target is `just ci` plus browser visual/smoke checks, not hardware UAT.

## Acceptance Criteria

- [ ] Desktop screenshot/browser view matches the v3 design direction for tokens, TopBar, pads, and variation controls.
- [ ] iPad-sized screenshot/browser view uses the stacked/responsive layout without clipped controls or inaccessible pads.
- [ ] iPhone landscape screenshot/browser view remains usable, scrollable where necessary, and free of incoherent overlap.
- [ ] TopBar C2 exposes every existing routing/tempo/performance control, including BPM visible but read-only under external clock.
- [ ] Pad pointer and keyboard interactions preserve held/latched visual behavior, with orange used only for currently sounding or latched pads.
- [ ] Per-style variation controls map exactly to existing variation indices and do not change engine playback semantics.
- [ ] Rhythm Gate gate control remains available for Rhythm Gate styles and absent for non-Rhythm styles.
- [ ] No progression rail, progression authoring, sequencer UI, or queued/countdown toast is added in this phase.
- [ ] `just ci` passes.
- [ ] Browser smoke passes for pad press/release, latch, bank navigation, transpose, style/variation changes, gate, clock source selection, BPM editing, and MIDI routing control reachability.
